# Teranode rejection reasons: what reaches arcade

A transaction arcade marks `REJECTED` must carry a reason its submitter can act on, and a
transaction teranode did not reject must never be terminalized. Both depend on a boundary arcade
does not own. This document is the audit of that boundary: for every teranode failure class, what
arrives on the wire, what arcade does with it, and what is still lost.

**Revisions audited.** arcade `main`; teranode `origin/main` @ `859c848f5`, whose `errors/`,
`services/propagation/Server.go` and `services/validator/` are identical to the pinned dependency
`github.com/bsv-blockchain/teranode v0.16.0-beta-9`.

**Kept honest by** `services/propagation/teranode_reason_contract_test.go`. Every row below is a
case in that table, and every fixture is generated by teranode's own error constructors rendered
through its own `errors.UserMessage` — never hand-written. A teranode module bump that changes the
boundary fails those tests instead of silently changing production behaviour.

## How the boundary works

1. **teranode collapses the chain.** `errors.UserMessage` (`errors/errors.go`) returns
   `DeepestPublicCause(err)` when the wrapped chain contains a code on `publicCauseCodes` —
   `UTXO_NON_FINAL, TX_LOCK_TIME, TX_POLICY, TX_INVALID, TX_INVALID_DOUBLE_SPEND, TX_CONFLICTING,
   UTXO_SPENT, TX_LOCKED` — and otherwise the **outermost** code and message. Everything else in
   the chain is dropped, including the actual BDK script error. Both surfaces use it: `POST /tx`
   and `POST /txs`.
2. **The txid lives in the wrapper that gets dropped.** The outermost error is
   `NewProcessingError("[ProcessTransaction][%s] failed to validate transaction", txID, err)`.
   When an allowlisted cause wins, that wrapper — and with it the only guaranteed txid — is
   discarded, and most inner messages name no transaction.
3. **arcade binds verdicts by reading the line.** `parseTxsFailures` keys each line by
   `[ProcessTransaction][<txid>]`, else the first bare 64-hex string. Lines that key to a hash
   nobody submitted ("alien" — a spent outpoint, a competing spender, a parent record) are
   re-attributed by outpoint against the submitted transactions' own inputs. Lines that key to
   nothing at all, and alien lines attribution cannot place, trigger **narrowing**: the chunk is
   re-broadcast in halves until the line is the only answer to a single transaction.

Narrowing is what makes an unplaceable verdict land. Cost is bounded at ~2·log2(n) extra requests
and only on the failure path; a response whose every line names its transaction settles in one
round trip.

## Broadcast modes

There is one network path: `POST /txs`, chunked by `Propagation.TeranodeMaxBatchSize` (default
1024). "Single mode" is that setting at 1 — a chunk of one is just one transaction's bytes.
`teranode.Client.SubmitTransaction` (`POST /tx`) exists but no caller uses it.

Both modes now reach the same verdict for every row below. They did not before: single mode
recovered two rows that batch mode lost, and both lost the thirteen rows whose line carries no
txid at all.

## The matrix

**Outcome** — ✅ terminalizes `REJECTED` with a cause-specific reason; ⚠️ terminalizes but the
reason is only as good as what crossed the boundary; ⟳ correctly does **not** terminalize
(condition or node fault) and retries.

Assumes one healthy endpoint. With several, any peer answering 200 accepts the transaction and
masks every row.

### C. BDK script / policy engine (`services/validator/ScriptVerifierGoBDK.go`)

`errMsgInvalidTx = "GoBDK fail to ValidateTransaction"`; `errMsgPolicy` appends
`" by policy settings"`. The real script error is a plain (non-`*Error`) wrapped cause, so
`DeepestPublicCause` can never select it and it is always dropped.

| # | Failure | Line on the wire | txid? | Outcome |
|---|---|---|---|---|
| C1 | any script eval failure (bad signature, `EVAL_FALSE`, DER, …) | `TX_INVALID (31): GoBDK fail to ValidateTransaction` | no | ⚠️ **upstream gap** |
| C2 | DoS: not-standard / sigops / non-free consolidation | `TX_POLICY (39): GoBDK fail to ValidateTransaction by policy settings` | no | ⚠️ **upstream gap** |
| C3 | fee below the node's floor | `TX_POLICY (39): transaction fee is too low` | no | ✅ via narrowing |
| C4 | policy-related script errors (op count, script size, stack size) | as C2 | no | ⚠️ **upstream gap** |
| C5 | CGO exception | `PROCESSING (4): [ProcessTransaction][<txid>] failed to validate transaction` | yes | ⟳ node fault (500) |
| C6 | height/int conversion | as C5 | yes | ⟳ node fault (500) |

C1/C2/C4 are attributed to the right transaction and terminalize, but the reason a wallet reads is
a constant string. **No arcade change can fix this** — the detail never crosses the boundary.

| D8 | coinbase immature | `PROCESSING (4): …` | own txid | ⚠️ **upstream gap** |
| D9 | duplicate submission | omitted from the body (classified 200) | — | accepted, correct |
| D10 | block assembly unavailable | `PROCESSING (4): …` + HTTP 500 | own txid | ⟳ node fault |
| D11 | other spend failures | `PROCESSING (4): …` + HTTP 500 | own txid | ⟳ node fault |

D1 renders as `TX_LOCK_TIME`, not `UTXO_NON_FINAL`: `util.IsTransactionFinal` returns a lock-time
error that `Validator.Validate` wraps in `NewUtxoNonFinalError`, and both codes are allowlisted, so
the **innermost** wins and the `[Validate][<txid>]` wrapper is dropped with the outer one.

D2 matters most. Because `TX_MISSING_PARENT` is not allowlisted, `lineIsMissingParentCondition`
can never match on this path, and every out-of-order child used to terminalize as a permanent
`REJECTED` — then cascade `parent rejected (ancestor …)` onto its own descendants. arcade now
recovers it from the HTTP status: 422 is reachable from exactly one branch of teranode's
`httpStatusForTxError`, `ErrTxMissingParent`, so a 422 carrying the opaque catch-all *is* a missing
parent. The status is only consulted when the peer reported a single failure, where it describes
that one transaction exactly.

An *opaque* line — `PROCESSING` with no nested named code, per `lineIsOpaqueProcessing` — is the
only shape for which the status is read at all, and it never terminalizes without it. When several
failures share one body the status is an aggregate that describes none of them individually, so
such a line requeues rather than being turned into a verdict; it ends, if it keeps failing, through
the durable-retry budget with the line quoted in the give-up reason. A line carrying any code other
than `PROCESSING` is a verdict regardless of the status, wrapper or not.

### E. Response-level

| Situation | Behaviour |
|---|---|
| 502/503, bare 500, no failure-list body, truncated body | no per-tx vote → requeue |
| some lines placed, others not | placed verdicts kept; no implicit accepts; chunk narrowed |
| every line placed | absent ⇒ accepted, including transactions an attributed line did not name |
| opaque `PROCESSING` alone in the body | classified by the peer's status (422 / 403 / 5xx) |
| opaque `PROCESSING` sharing a body with other failures | status is ambiguous → requeue, never REJECTED |
| multi-endpoint, one peer accepts | acceptance is sticky and masks every row above |

## What is still lost, and where it has to be fixed

Three gaps remain, all inside teranode's error boundary:

1. **BDK script and policy causes** (C1, C2, C4). `mapBDKValidationError` wraps the real
   `ScriptError`/`DoSError` as a plain error under `TX_INVALID`/`TX_POLICY`, so only the constant
   message survives. Fix: carry the cause (at minimum its code) into the message itself.
2. **`ERR_TX_MISSING_PARENT` is not allowlisted** (D2). arcade recovers the class from the 422, but
   only when the peer reported a single failure. Allowlisting it — it is a client-safe, actionable
   verdict naming no internal state — restores the direct signal.
3. **`ERR_UTXO_FROZEN` / `ERR_TX_COINBASE_IMMATURE` are not allowlisted** (D7, D8). Frozen is
   recoverable from the 403; coinbase-immature is not distinguishable at all.

A fourth change would retire narrowing entirely: have `/tx` and `/txs` render each failure as
`CODE (n): [ProcessTransaction][<txid>] message`, keeping the code at the head of the line so
existing parsing is unaffected. That single change gives every row in A, B and C a txid.

Until those land, `TestTeranodeRejectionReasonContract` pins each gap with an `upstreamGap` note
and an `absentToken` that must stay absent — so when teranode starts carrying the real cause, the
row fails and gets promoted rather than quietly staying stale.
